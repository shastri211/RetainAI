# Phase 1 — Data and Model Pipeline

Scope: a clean, reproducible, tested foundation for customer risk, model-grounded reasons and revenue-exposure proxies on the IBM Telco sample (PUBLIC data for a fictional company). No LLM, RAG, uplift, agents, vector store, database or deployment infrastructure is part of this phase.

Numbers below are copied from the committed reports (`reports/baseline_metrics.json`, `reports/fairness_audit.json`, `reports/value_summary.json`, `reports/data_validation.json`) and are regenerated by the commands in the README. `tests/test_docs.py` checks that they still match.

## 1. Data flow

```
data/raw/Telco-Customer-Churn.csv      immutable, never written to
        │  load_raw (all fields as text; blanks stay visible)
        ▼
validate_raw  ── ERROR stops the pipeline · WARNING/INFO are reported ──►  reports/data_validation.json
        │
        ▼
clean_telco                              data/processed/telco_cleaned.csv   (audit flags, not model inputs)
        │
        ▼
derive_features (stateless, row-wise)    data/processed/telco_features.csv  (model-ready table)
        │
        ▼
Pipeline = ColumnTransformer + estimator (fitted only on training rows, stored with the model)
        │
        ▼
models/churn_baseline/{model.joblib, metadata.json}   (git-ignored)
```

`data/processed/` and `models/` hold generated files and are git-ignored. Every step is deterministic: the same input gives byte-identical processed tables, reports and model version.

The dataset fingerprint is the SHA-256 of the file with line endings normalised to LF (`16320c9c1ec72448…`). Git stores the CSV with LF while Windows checkouts get CRLF, so a raw-byte hash would differ between machines.

## 2. Dataset contract

Defined once in `src/retainai/data/schema.py`.

| Role | Columns |
|---|---|
| Identifier (never a feature) | `customerID` → `customer_id` |
| Target | `Churn` → `churn` (`Yes` = 1) |
| Numeric | `tenure` (whole months, ≥ 0), `MonthlyCharges` (> 0), `TotalCharges` (≥ 0 or blank) |
| Binary 0/1 | `SeniorCitizen` |
| Yes/No categorical | `Partner`, `Dependents`, `PhoneService`, `PaperlessBilling` |
| Categorical with structural values | `MultipleLines` (`No phone service`), the six internet add-ons (`No internet service`) |
| Other categorical | `gender`, `InternetService`, `Contract`, `PaymentMethod` |

Missing values: no blank cell is accepted anywhere except `TotalCharges` when `tenure = 0` (KI-1). Anything else is an ERROR.

Checks (each with a severity): required and unexpected columns, non-empty table, unique and well-formed IDs, whitespace padding, blanks, numeric parsing and finiteness, ranges, categorical domains, target labels and presence of both classes, structural consistency (`MultipleLines` vs `PhoneService`, add-ons vs `InternetService`), billing consistency (`tenure = 0` ⇔ nothing billed; `tenure > 0` ⇒ positive total), duplicates, contract term vs tenure, and `TotalCharges` vs `tenure × MonthlyCharges`.

## 3. Known issues and chosen treatment

Nothing is silently fixed. Each issue is detected, reported under a stable ID, and handled by a stated rule.

| ID | Issue (measured) | Treatment | Rationale |
|---|---|---|---|
| KI-1 | 11 blank `TotalCharges`, all `tenure = 0`, all `Churn = No` | Set to 0.0, flag `total_charges_was_blank`; rows kept. Blank with `tenure > 0` is an ERROR. | A customer with no tenure has been billed nothing; keeping the rows lets brand-new customers be scored. The earlier exploratory notebook dropped them. |
| KI-2 | 22 extra rows (20 groups) identical on all non-ID columns; every group is at `tenure = 1` | Rows kept; `duplicate_group_id` assigned; all splits keep a group on one side. | Distinct customer IDs and `TotalCharges = MonthlyCharges` at tenure 1 (613 of 613 rows) make coincidence the likely explanation. Group-aware splitting is a cheap precaution. |
| KI-3 | 142 two-year-contract rows with tenure < 24 (none churned); 102 one-year rows with tenure < 12 (8 churned) | Nothing changed; reported as INFO; `contract_term_exceeds_tenure` audit flag. | Plausibly still in the first term; not an inconsistency. The undocumented *time reference* of `Contract` is tested by an ablation instead (section 6). |
| KI-4 | `TotalCharges` within 2% of `tenure × MonthlyCharges` for 50% of rows (5th–95th percentile ≈ −7.6% to +7.5%) | Not corrected. Reported as INFO; only gross deviation (> 100%) warns. | Prices change; equality was never a valid assumption. |

Corrections to the Phase 0 reading of KI-2/KI-3 and the withdrawal of a survival-based CLV are recorded in `DECISIONS.md` D-18.

## 4. Target

`target = churn`, positive class `Yes` → 1, negative `No` → 0. All 7,043 rows are used (1,869 positive, prevalence 0.2654).

Limitations of this target:

- A single static snapshot; there is no time dimension and no way to validate forward in time.
- The churn horizon is not in the data, so a score is "probability of `Churn = Yes` as defined in this dataset", not "within N days". No horizon is invented anywhere.
- Observational: no intervention history, so nothing here says what would change a customer's outcome.

## 5. Features

Stateless derivation (`derive_features`) then a fit-time preprocessor (`make_preprocessor`).

| Group | Features |
|---|---|
| Numeric (standardised) | `tenure_months`, `monthly_charges`, `total_charges`, `num_addon_services` (count of the six add-ons that are "Yes") |
| Binary 0/1 | `partner`, `dependents`, `phone_service`, `paperless_billing`, `multiple_lines`, and the six add-ons (`No phone/internet service` → 0, because `phone_service` / `internet_service` already carry it) |
| One-hot | `internet_service`, `contract`, `payment_method` |

Excluded from the model: customer ID, target, audit flags, `duplicate_group_id`, and the protected attributes `gender` and `senior_citizen` (retained only for the subgroup audit). Unseen categories at inference encode to zeros instead of failing. The derivation is row-wise, so a customer's features are the same alone or in a batch, and the same code path serves training and scoring (including customers with no `Churn` column).

`total_charges`, `tenure_months` and `monthly_charges` are collinear. Their individual contributions should not be read separately.

## 6. Models and evaluation

Protocol (`src/retainai/models/baseline.py`): a stratified, duplicate-group-aware 20% holdout (5,634 dev / 1,409 test); 5-fold × 3-repeat stratified grouped CV on the dev rows with identical folds for every model and ablation; thresholds, calibration and capacity from out-of-fold predictions averaged over repeats; the holdout used once for reporting. No hyperparameter search.

| Model | CV ROC-AUC | CV PR-AUC | CV Brier | Holdout ROC-AUC | Holdout PR-AUC |
|---|---|---|---|---|---|
| Prior (no features) | 0.500 | 0.265 | 0.195 | 0.500 | 0.265 |
| **Logistic regression (shipped)** | 0.840 ± 0.013 | 0.652 ± 0.024 | 0.137 | 0.863 | 0.684 |
| Random forest | 0.839 ± 0.013 | 0.654 ± 0.019 | 0.137 | 0.860 | 0.680 |
| Hist. gradient boosting | 0.841 ± 0.011 | 0.658 ± 0.020 | 0.137 | 0.866 | 0.701 |

± is the SD across the 15 folds and understates true uncertainty because folds share training data. The tree models are within one fold-level SD of logistic regression, so the interpretable model ships; if a benchmark ever beats it by more than one SD, the report flags it for an owner decision instead of switching. The holdout is one 1,409-row sample; do not rank models on its differences.

**Calibration:** expected calibration error 0.014 on dev out-of-fold predictions and 0.025 on the holdout (5 bins). No calibrator was added.

**Threshold selection (not 0.5 by default).** With no intervention cost, offer or capacity data, three views are reported (dev out-of-fold, shipped model):

- *F1-optimal threshold 0.29.* On the holdout: precision 0.552, recall 0.770, F1 0.643 (tn 801, fp 234, fn 86, tp 288). At 0.5 the holdout gives precision 0.702, recall 0.553, F1 0.619 (tn 947, fp 88, fn 167, tp 207).
- *Capacity view.* Contacting the top 10% by score captures 28% of churners at precision 0.753 (lift 2.84); the top 30% captures 65% at precision 0.579.
- *Assumed-cost sensitivity.* If a missed churner were 1, 2, 3, 5 or 10 times worse than an unnecessary contact, the cost-minimising thresholds are 0.55, 0.33, 0.26, 0.16 and 0.09. These ratios are **assumptions** (labelled `ASSUMED` in the report), not data.

The right operating point depends on contact cost and capacity, which are business inputs that do not exist yet.

**Ablations (paired on the same folds, change in CV PR-AUC vs default):** adding the protected attributes −0.002 (SD of paired differences 0.007); removing `Contract` −0.005 (SD 0.006); removing `TotalCharges` −0.001; removing both −0.006. Protected attributes add nothing measurable, so excluding them costs nothing here. `Contract` carries signal, but removing it changes PR-AUC little, so there is no sign that it alone drives the result through leakage. This does not rule out a time-reference problem inside `Contract`.

## 7. Risk scoring

`retainai score` produces one record per customer (`src/retainai/scoring/risk.py`):

```
customer_id, risk_score (0-1, from the model), risk_band, model_version,
prediction_timestamp, top_reasons, in_sample
```

- `risk_score` is the shipped model's predicted probability, rounded to 6 decimals. Nothing else touches it.
- Bands are lower-inclusive: **LOW** < 0.25, **MEDIUM** 0.25 to < 0.50, **HIGH** ≥ 0.50. Cutoffs come from the meaning of a calibrated probability (0.25 is about the 0.265 base rate; 0.50 is "more likely than not"), not from tuning on outcomes. They are communication labels, not decision thresholds. Observed churn per band: holdout LOW 0.090 (n = 849), MEDIUM 0.343 (265), HIGH 0.702 (295); dev out-of-fold 0.088, 0.352, 0.647.
- `top_reasons` is empty unless the explainer fills it; reasons are never invented.
- `in_sample` is true when the scored file is the model's own training file; those scores are optimistic and the CLI warns.
- `model_version` is content-derived (dataset hash, feature pipeline, hyperparameters, seed, library version): `churn-lr-633166dbf0` for the committed run.

## 8. Explainability

For the shipped logistic regression, the contribution of an original feature is the sum, over its encoded columns, of `coefficient × (value − training mean)`. The contributions add up exactly to the model's own log-odds minus the log-odds of the average training profile (a tested invariant), so every reason is tied to what the model computed. `top_reasons` lists up to `k` (default 3) risk-increasing features, largest first, with their values and magnitudes; customers with nothing pushing risk up get none.

Three different things must stay separate:

| Level | Available? | Meaning here |
|---|---|---|
| **Model signal** | Yes (`evidence_type = MODEL_SIGNAL`) | How the fitted model moves its estimate relative to the average customer. |
| **Business interpretation** | Not generated | What a pattern might mean commercially is a human judgement; the code never writes it. |
| **Causal explanation** | **No** (`causal_claim` is fixed to `false`) | The data is observational with no interventions, so a contribution is a pattern in the data, not a proven cause or the effect of changing the feature. |

Global importance (mean absolute contribution in log-odds): `tenure_months` 1.26, `total_charges` 0.58, `contract` 0.52, `monthly_charges` 0.40, `internet_service` 0.27. Reasons are relative to the average customer, so for a LOW-risk customer the listed factors are small and do not mean the customer is at high risk. Non-linear models are refused rather than approximated.

## 9. Value / revenue at risk (proxies only)

Built only from `MonthlyCharges` and `TotalCharges`. No margin, cost-to-serve, discount rate, horizon or future billing exists. A survival-based CLV was rejected (D-18).

| Output | Basis |
|---|---|
| `monthly_revenue` | OBSERVED: `MonthlyCharges` as reported |
| `revenue_to_date` | OBSERVED: `TotalCharges` as reported (0.0 for the 11 never-billed rows) |
| `revenue_at_risk_monthly` | DERIVED: `risk_score × monthly_revenue`; implies no time horizon |
| `clv_proxy` | **ASSUMED**: `monthly_revenue × assumed_months` (default 12, configurable); revenue not margin; not a true CLV |
| `clv_at_risk_proxy` | DERIVED + ASSUMED: `risk_score × clv_proxy` |

On the full file the risk-weighted monthly revenue at risk is 139,153 against total monthly revenue of 456,117 (fictional currency units); the observed monthly revenue of customers who actually churned is 139,131. That near-equality is a consistency check, not validation: scoring the training file is in-sample, and a logistic regression with an intercept reproduces the mean outcome by construction.

## 10. Subgroup audit

`reports/fairness_audit.json` covers gender, senior citizen, partner and dependents on dev out-of-fold predictions (primary) and the holdout (secondary), with seeded bootstrap 95% intervals. It is **descriptive and gives no fairness verdict.**

| Attribute | Used by the model? | Retained for |
|---|---|---|
| `gender` | No | audit only |
| `senior_citizen` | No | audit only (ablation shows no accuracy gain from using it) |
| `partner`, `dependents` | Yes | audited (family status can proxy for age or marital status) |

What it shows (dev out-of-fold, at the F1-optimal threshold 0.29):

- **Gender:** no detectable gaps in discrimination, calibration, selection rate or error rates.
- **Senior citizens (not a model input):** observed churn 0.424 vs 0.235. They are flagged far more often (selection rate 0.605 vs 0.345), with a higher true-positive rate (0.847 vs 0.745) and about double the false-positive rate (0.427 vs 0.223). Discrimination is lower (AUC 0.796 vs 0.841; difference −0.045, interval −0.077 to −0.014) and the model under-predicts slightly (mean predicted 0.392 vs observed 0.424). Excluding the attribute did not remove its proxies. These gaps are tied to a much higher base churn rate; whether they are acceptable depends on whether an intervention is a benefit or a burden, which is undecided. The holdout has only 235 seniors and shows the same direction with wider intervals.
- **Partner / dependents:** similar base-rate-linked differences in error rates.

Limits: other attributes and intersections are not covered; intervals exclude model-fitting uncertainty; small groups are flagged, not scored; the audit does not establish fairness or its absence.

## 11. Reproducibility and metadata

`models/churn_baseline/metadata.json` records: model version, model type, hyperparameters, training timestamp (UTC), seed, dataset SHA-256 and provenance label, feature pipeline version and feature list, evaluation metrics (CV and holdout), operating thresholds, risk-band cutoffs, the explanation reference profile, and library versions. Training twice with the same seed gives byte-identical reports and the same model version; only the timestamp differs. No experiment-tracking platform is used.

`joblib` files are pickles: load only models this project produced locally.

## 12. Commands

| Command | Purpose |
|---|---|
| `python -m retainai validate` | Validate the raw CSV; writes `reports/data_validation.json` |
| `python -m retainai prepare` | Validate, then write the cleaned and model-ready tables to `data/processed/` |
| `python -m retainai train` | Train and evaluate the candidates; save the shipped model; write the baseline and fairness reports (about 2–3 minutes) |

## 13. Known limitations

- Fictional-company sample data; results say nothing about any real customer base.
- Static snapshot with an undefined churn horizon; no temporal validation; scores are not "probability within N days".
- Small data: wide uncertainty; the 20% holdout is a single sample.
- All reasons and importances are associations; there is no causal claim and no treatment effect.
- Value outputs are proxies; the CLV proxy rests on an assumed number of months.
- Group disparities exist for senior citizens, partner and dependents; no decision rule has been set for how scores will be used.
- The time reference of `Contract` is undocumented.
- Cost-based thresholds use assumed ratios.
- The exploratory notebooks (`notebooks/`) need additional packages (matplotlib, seaborn, Jupyter) that are not in `requirements.txt`; they were not re-run in Phase 1.
